## 0. 结论

芯伴自己不写代码，它是 Claude Code / Codex / WorkBuddy 外面那一层。能立住的价值只有一句：

> **几个 AI 在后台干活，芯伴告诉我谁在等我；我在它身上按一下或说一句，AI 就接着干。**

「派出去」「看进度」已经通了（派活真机验过、钩子收到真实事件、评测派活 18/18）。
缺的是后半段：**外部 Agent 停下来问权限时，芯伴接不住**——`xinban-hook.cjs` 在 `PermissionRequest`
上只会按「替你确认」规则自动批准，判断不了就什么都不输出，你还得回终端点。小屏、A/B 键、面板确认卡
目前只管芯伴自己的工具。

本轮按顺序做七件事（第 2–8 节），做完自用两周，用数据决定要不要往产品走。

## 3. M1 远程批准外部 Agent 的权限请求（核心）

### 3.1 目标

Claude Code（及同格式的 WorkBuddy / CodeBuddy）弹权限请求时，芯伴桌宠小屏、面板、（之后）实体 A/B 键
同时亮出确认卡：命令原文 + 项目 + 风险等级。你在任意一处允许/拒绝，Agent 当场继续；没人理就退回终端照常弹窗。

### 3.2 流程

```
Agent 触发 PermissionRequest
  └─ xinban-hook.cjs（同步）
       1. classify() 算风险与指纹（已有）
       2. decide() 替你确认命中 → 直接 allow（已有，保持不变）
       3. 芯伴不在线（心跳过期）或远程批准关着 → 不输出，退回终端（已有行为）
       4. 新增：写 pending/<id>.json → 轮询 decisions/<id>.json（每 200ms）
            ├─ allow → 输出 decision.behavior = allow
            ├─ deny  → 输出 decision.behavior = deny（带一句原因）
            └─ 超时 / 芯伴下线 / 任何异常 → 不输出，退回终端
       5. 删掉自己的 pending 文件；记一条收件箱事件（结果 + 用时，不记参数原文）
芯伴主进程
  └─ 监听 pending/ → 进确认队列 → 小屏/面板/实体键 → 写 decisions/<id>.json（原子写）
```

### 3.3 设计要点

- **通信沿用文件，不开端口**：和现有收件箱/`approve.json` 一致，不引入本机网络面。目录放
  `userData/hooks/` 下，pending/decisions 两个子目录。
- **防错配**：decision 文件必须带同一个 `id` 和请求指纹 `fp`；对不上就当没有。`id` 用随机 UUID。
  启动时清理超过 10 分钟的残留文件。
- **等待时长**：钩子 `timeout` 从 10 秒提到「等待时长 + 5 秒」。默认等待建议 **45 秒**（见第 9 节拍板）。
  ⚠ 钩子等待期间终端弹窗不会出现——这是代价。面板提供「立即交回终端」按钮，写一个 `defer` 决定，钩子立刻不输出退出。
- **确认卡复用现有 ConfirmService**：新增 `ConfirmTool = 'agent_permission'`；
  卡片标题「Claude Code 想 运行命令」，详情 = 命令/文件路径原文。超 800 字的不进芯伴，直接交回终端。
  实体小屏规则不变：只有 24 字内可打印 ASCII 能在设备上批准，其余只能拒绝或去桌面看全文。
- **超时语义不同**：芯伴自己的工具超时 = 拒绝；外部 Agent 超时 = **交回终端**（不替你拒，也不替你批）。
- **与排队上限的关系**：外部请求单独一条队列（上限 4），不挤占芯伴自己工具的确认。
- **「以后同类都批」**：卡片上加第三个按钮，等同于在替你确认里加一条规则（复用 `approve.json`
  与 v4 规则，高风险永远不出现这个按钮）。替你确认仍默认关，这个按钮是唯一入口。
- **Codex 不做**：Codex 只有 `notify`，没有能回传决定的同步钩子；工作台里只显示「在等你，回终端处理」。
- **日志**：只记 来源/工具名/风险/结果/用时，不记命令原文（遵守日志规则）。

### 3.5 测试

- 单测（直接 `require` 钩子脚本，用临时目录）：allow / deny / 超时 / defer / 芯伴下线 / 指纹不符 /
  decision 文件半写入 / 并发两个请求互不串 / 替你确认命中时不进入等待。
- E2E：假钩子进程写 pending → 面板出卡 → 点允许 → 钩子 stdout 为 allow；点「交回终端」→ stdout 为空。
- 真机（M4 一并做）：真实 Claude Code 跑一条需要批准的命令，在桌宠上批准，看它接着干；再测超时交回终端。
- 待查证：WorkBuddy / CodeBuddy 是否认 `deny` 和 `allow` 输出（目前只证明它们收得到事件）。

### 3.6 验收

- 真实 Claude Code 中，从弹请求到桌宠出卡 < 1 秒；批准后 Agent 继续。
- 超时、芯伴关闭、钩子异常三种情况下，终端照常弹窗，Agent 不会被卡死也不会被替你决定。

## 4. M2「工作台」：谁在等我

### 4.1 目标

一眼看清所有 Agent：**等你（最上） → 出错 → 干完没看 → 在干 → 空闲**。面板一张卡、桌宠小屏一行摘要
（如「2 个等你 · 1 个干完」），实体小屏同样显示摘要。

### 4.2 数据来源（都已有，只是合并）

| 来源                         | 提供                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| 钩子会话（`hook-events.ts`） | 各 Agent 会话的 waiting/working/done、项目目录、最近一句提示 |
| 派活记录（`delegate.ts`）    | 芯伴派出去的活：目标、项目、用时、退出码、失败原因           |
| M1 外部确认队列              | 具体在等哪一条命令                                           |

### 4.3 新增的状态

- **干完没看**：`done`（或派活成功结束）后，直到你在工作台点开、或在该项目里发了新提示，才清除。
  需要一个按会话的「已看」标记，存在 `progress` 状态里，重启不丢。
- **出错**：派活非零退出、超时；钩子会话异常结束。
- 同一项目多个会话按项目分组；会话名用 `项目名 · Agent`。

### 4.4 交互

- 点「等你」那行 → 直接打开 M1 的确认卡；Codex 的 → 提示回终端。
- 点「干完没看」 → 打开 M3 的结果卡。
- 主动开口接上：有 Agent 等你超过 2 分钟且你没看 → 桌宠提醒一次（走现有打扰预算，勿扰时不出声）。

### 4.5 验收

- 3 个会话（Claude 等你、Codex 在干、WorkBuddy 干完）同时存在时，排序和计数正确；重启后「干完没看」不丢。
- 单测覆盖排序、已看标记、过期（`waitingFreshMs` 15 分钟）规则。

## 5. M3 干完可审

### 5.1 结果卡内容

1. Agent 最后一句结论（派活已有；钩子会话用 `Stop` 时的最后提示/会话尾部摘要）。
2. **改了什么**：在项目目录只读执行 `git status --porcelain` 与 `git diff --stat`，列出文件和增删行数；
   不是 git 仓库就写「不是 git 项目，看不到改动」。
3. **测试结果**：只从 Agent 输出里识别常见摘要行（vitest/jest/pytest/mvn/go test 的 passed/failed 行），
   识别不到就不显示。**不由芯伴自己去跑测试**（会改环境、耗时、可能有副作用）。
4. 按钮：「在编辑器打开」（可配置命令，默认 `code <项目目录>`）、「看完整 diff」（面板内只读展示，限长）、
   「接着说」（对同一 Agent 追加一条指令，复用派活）、「标记已看」。

### 5.2 约束

- git 命令走现有 `run_command` 的白名单思路：固定参数、只读、限时 5 秒、输出限长。
- diff 内容只在面板显示，不写日志、不进记忆、不发给模型（除非你点「让伙伴总结」）。

### 5.3 验收

- 派一个真实小任务，干完后结果卡里的文件列表与 `git diff --stat` 一致；「在编辑器打开」能打开对应目录。

## 10. 风险

- **官方在补同样的能力**：Claude Code 已有通知、手机远程与更宽松的权限模式，需要人批的场景在变少。
  芯伴守得住的是「跨厂商一个总览」和「一个物理按键」。
- **钩子格式会变**：四家工具任何一次升级都可能让钩子失效；依赖钩子自检兜底，每次大版本手动回归一次。
- **同步钩子拖慢终端**：等待期间终端不弹窗，体验不好就调短等待或默认关。
- **没做市场调研**：两周自用数据只能说明「对你有没有用」，不代表别人愿意装、愿意付费。

## 附录 A：定位与市场判断（2026-11-11 讨论记录）

以下是判断，没有做市场调研、没有数据支撑。

- **大众 AI 桌宠 / 智能音箱定位：难。** 开源的小智 AI（xiaozhi-esp32）已把「ESP32 + 语音 + 大模型 + MCP + 家电」
  做成一两百元的成品且生态大；大厂音箱占着家电入口；「又一个和 AI 说话的盒子」很难卖。芯伴在这条线上没有优势。
- **编程搭档定位：有特色但市场小。** 独有的是跨厂商派活 + 盯进度 + 实体键批准。
  作为个人工具能立住；作为产品要先补上 M1–M3 的闭环，并用 M7 自用数据验证。
- 用户已决定：先只按「编程助手」定位考虑，物联网暂放。

## 附录 B：物联网讨论记录（暂停，留待以后）

### B.1 现状（核对代码）

- 固件（`firmware/xinban-device/src/main.cpp`）：独立 FreeRTOS 任务每 3 秒轮询，支持 Tasmota / Shelly 第二代 /
  ESPHome 三类局域网 HTTP 开关，开关 + 在线 + 功率，最多 8 台，登记表存 NVS；脱离电脑时小屏 + A/B 也能控。
  WiFiManager 用手机热点配网。
- 主机（`src/core/iot.ts`、`src/desktop/device.ts`）：面板登记设备，帧 `iot.config / iot.set / iot.state / iot.net`。
  控制路径是「电脑 → 串口 → ESP32 → 设备」，电脑不直连设备。
- **AI 不能控制**（有意设计，`docs/hardware-protocol.md`），只能面板手点。
- 只在模拟中枢上跑通，没碰过真设备。设备模型只有「开关」，放不下传感器/空调状态/红外键。
- 国内主流家电（米家、涂鸦、红外遥控的空调/电视）基本没覆盖。

### B.2 三种方式的可行性

- **红外**：IRremoteESP8266 自带格力/美的/海尔/大金/海信等空调完整状态协议；接收头可学习任意遥控器。
  **单向，读不到真实状态**，只能显示「最后发了什么」。需要：940nm 发射管 + S8050 + 电阻 + VS1838B（几块钱）。
- **蓝牙**：ESP32-S3 只有 BLE，**没有经典蓝牙**（蓝牙音箱/耳机连不了）。适合读 BTHome 传感器、刷 pvvx 的
  小米温湿度计 LYWSD03MMC；米家原厂 BLE 要 bindkey。可控的只有协议公开的（如 SwitchBot）。用 NimBLE 省内存。
- **WiFi**：mDNS 自动发现 ESPHome/Shelly/Tasmota；米家（miIO/MIoT）、涂鸦本地协议可行但每台要 token / local key。

### B.3 「查看局域网内所有设备实时状态」的分层方案（用户最想要的）

1. **第一层：发现所有设备 + 在线状态**（好做、不挑品牌、不要密钥）：ARP 扫描拿 IP/MAC 和上下线；
   MAC 前缀认厂商；mDNS/SSDP 认类型（米家 `_miio`、DLNA/投屏、HomeKit `_hap`）。限制：手机休眠会时断时续；
   AP 隔离/访客网络扫不到。
2. **第二层：设备内部状态**：米家 WiFi（token，小米账号登录一次导出）、涂鸦（local key，开发者账号导出）、
   格力 WiFi 空调（局域网内可绑定，门槛最低）、美的（部分型号，需云端取密钥）；只走云的设备做不到。
   具体型号能否可行需逐个试。
3. **第三层：笨电器**：带计量的智能插座看功率判断开/待机/运行（现有固件已能读功率）。

### B.4 重启时要讨论的

- 先做第一层设备发现？先把协议从「开关」扩成「能力」（开关/传感器/空调/红外键）？
- 家里实际品牌（米家/涂鸦/格力/美的…），决定第二层顺序。
- AI 是否可以控制家电（建议每次弹确认卡）。
- 替代路线：接 Home Assistant 的 MCP 服务（不需 ESP32，覆盖米家/涂鸦/红外），或让电脑直连设备。
