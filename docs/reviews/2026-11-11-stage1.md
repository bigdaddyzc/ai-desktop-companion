## 3. 是否所有软件功能都完整测试过？

**没有。** 上表给出可核对的范围，不使用“全部功能无问题”结论。常规自动化通过且补充探针失败并不矛盾：它们检验的情境不同，失败情境不能从总结果中删掉。

本轮覆盖：本地状态、待办/计时、跨窗口同步与重启、导入导出、配置持久化、手势、记忆管理、主动提醒、模型/工具服务逻辑、权限与路径已有规则、模拟硬件与 IoT、MCP 本地假服务器、官方钩子测试替身；语音/视觉等只覆盖配置、权限和替身路径，不证明真实识别/播放质量。

以下仍未完成真实验收：

- 三条真实 DeepSeek E2E（对话、联网搜索、记忆），本轮无专用测试 Key，全部跳过；仓库里的历史真实 Key 记录不是本轮成绩。
- 中文 STT 准确率、TTS 听感、真实摄像头/屏幕视觉、实际音乐客户端。
- 认证后的第三方 CLI/Agent 真正派活、真实 MCP 服务与实体 IoT。
- 24 小时常驻、泄漏趋势、休眠恢复、多屏 DPI 组合、安装包、跨操作系统。
- ESP32 上电/烧录/CDC/复位、屏幕、电气、机械按键、并发任务、实机内存/栈、真实网络与供电。

## 4. 软件方面已经发现的实际问题（仍未修）

1. **高：写入的确认与最终提交之间缺少重新校验。** 确认期间撤写权限仍可写；用户改过的内容可能被旧 diff 覆盖；父目录在本地被换成 junction 后可能写到授权外；备份期间取消仍可能继续写。不是说普通路径可以任意逃逸，junction 复现需要本地并发替换条件。位置：`src/desktop/tools.ts` 的 `commitWrite`。
2. **高：改动索引落盘失败被吞。** 构造 journal 写失败后，文件已经改变且工具报 ok；重启后改动列表为 0，撤销链路不可靠。位置：`src/desktop/files.ts` 的 `saveChanges`。
3. **高：撤销没有用户后续编辑冲突检测。** 撤销会覆盖较新内容；现有撤销前备份提供恢复机会，但不能代替冲突确认。位置：`src/desktop/files.ts` 的 `undo`。
4. **中：MCP CRLF SSE 长连接解析失败。** LF 对照成功，合法 CRLF 响应直到 750ms 测试超时仍不返回，分隔逻辑只识别 `\n\n`。位置：`src/desktop/mcp-client.ts`。
5. **中/低：说明与版本展示滞后。** 部分安全文案仍写“只上传文字/不传屏幕/仅少数命令”，实际已有显式授权的附件/视觉/shell；不是暗传，但会误导用户。UI 仍有写死 0.2.0，与包版本 0.3.0 不符。

7 条失败用例归属前 4 类，并非 7 个独立根因；文案与版本问题来自代码审查。详情、复现前提及此前隔离 IPC 并发实测见 [原审计记录](2026-11-11-project-audit.md)。本阶段已经修复的协议两项不再列为未修。

**建议：重要目录保持只读，先把文件操作改成带权限/路径/内容/取消复核的提交事务，并补撤销冲突与 journal 失败处理；然后修 SSE 解析与说明。** 这比增加更多高风险工具更优先，不要求重做现有智能宿主。
