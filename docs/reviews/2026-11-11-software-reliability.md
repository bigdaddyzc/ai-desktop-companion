按用户“先解决软件问题，修好后完整模拟测试”的要求执行。项目仍以 ESP32 硬件桌面机器人为目标；本次验的是智能宿主、桌面模拟与异常恢复，不把它们等同于实体机器人验收。

## 重复与故障模拟具体做了什么

每轮重跑文件事务、MCP 流、AI 会话/服务、语音管线、设备服务/契约、持久化、记忆安全、确认服务和既有可靠性回归。不是只重复启动应用：

- 文件压力用例每轮连续修改同一文件 40 次，再并行创建 12 个不同文件；验证最终字节、重启后历史最多 30 条、备份有界、正常路径无暂存文件泄漏。
- 两个同旧版本的写入确认并发放行，只能提交一个；并发目录配置更新不丢条目。
- 每轮 MCP 做 20 组“挂起→超时取消→下一请求成功”，检查 20 次取消通知和 reader 解锁。
- 注入备份失败、两阶段日志失败、取消、授权失效、并发编辑、目录替换；恢复仅根据预写日志与磁盘核对，不盲目回滚用户数据。
- 文件撤销和冲突在真实 Electron 页面点击并检查磁盘，随后退出应用重新启动核验。

五轮脚本本机实测总耗时 35.17 秒（包含测试进程启动）。这是短时、有界、可复现的模拟，不是整机 24 小时 soak、内存泄漏长期测量或 99.9% 可用率证明。

## 仍需遵守的安全与可靠性边界

1. 原先七个失败场景已修复，并不等于证明不存在其它软件缺陷；未做全路径穷举或形式化验证。
2. 文件更改使用 Node 同步复核后立即 rename/unlink，消除了已复现的应用层等待窗口，但 OS 系统调用之间仍不具备目录句柄级 CAS 隔离。恶意本地进程最终竞态、跨文件系统、多系统兼容性未得到证明。
3. fsync 文件不等于断电级事务；未保证目录项在断电后一定持久。原文件与暂存文件的替换是单文件操作，不是多文件数据库事务。
4. 最终 journal 写失败可能意味着目标已经改变，界面会明确报出并冻结后续写/撤销；此时不要重复执行，保留备份/日志，重启核对。损坏日志不会自动重置，旧记录和冲突需人工处理。
5. 异常中断或父目录被移动可能留下备份、空目录或暂存文件；保守清理不跟随未知路径，避免为了清理而误删。备份不能代替 Git 或独立备份。
6. 真实云服务、外部 Agent/MCP、音频/视觉/媒体、IoT 和 ESP32 实机必须另做接入验收。硬件未购并不妨碍本轮软件回归，但不能据此宣布机器人已实机高可用。
