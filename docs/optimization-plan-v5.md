## 1. 定位：不是等硬件的模拟器，也不是另一个代码编辑器

### 一句话

> **芯伴是一个有伙伴感的桌面编程助手：帮你交代任务、盯住进度、处理需要你决定的事，并接住结果，让你少在 AI 工具之间来回切换。**

- 产品类别：个人桌面编程搭档，当前先服务 Windows 用户。
- 核心价值：减少管理 Agent 的注意力成本，而不是宣称比底层 Agent 更会写代码。
- 机器人形象：低打扰入口和个性表达，不是全部工作界面，也不是价值成立的必要条件。
- 工作台：任务、权限、结果与接入健康的事实中心。
- 实际执行者：已经接入的编程 Agent；芯伴自己的受控工具保留，但本轮不扩成另一套通用编程环境。
- 对话、记忆、语音：让交代任务和理解结果更自然；不要求每一步都先问模型。
- 硬件与智能家居：退出本轮主线，保留代码和历史文档，不采购、不删固件、不承诺恢复日期。

“独立桌面产品”指无需购买硬件也能完成有用流程，不代表离线大模型，也不代表电脑关机后继续执行任务。

### 对外介绍建议

> 几个 AI 在后台干活，你不用挨个盯。芯伴把谁在等你、哪里出错、什么结果待看放到一起；需要你时说明白，没事时安静待着。

这是目标表述。正式展示时只宣传能力清单里已实测的范围，不能把所有工具都能回传批准、任意原会话续接或无人值守验收写成现成功能。

## 2. 为谁做，解决什么问题

### 首要用户

先验证用户本人：经常跨项目使用编程 Agent，让任务在后台执行，同时自己继续做事。

扩展目标是具有同类工作方式的个人开发者。多 Agent 用户的价值机会更明显，但只用一个 Agent、经常等待长任务的用户也可能受益；不把“装了几种工具”当成使用需求。

### 三个核心问题

1. **不知道何时该回来处理**：任务可能在等待输入或授权，自己却还在别处忙。
2. **不知道哪条消息对应哪件事**：项目、会话、派活和权限请求分散，容易混淆或重复计数。
3. **不知道结束后该看什么**：Agent 说完成，不等于改动已核对、测试已验证、需求已验收。

### 暂不服务

- 只想装饰桌面、收集皮肤的用户：保留陪伴体验，但不走内容商店和养成路线。
- 需要完整 IDE、多人项目管理或复杂自动调度平台的团队。
- 需要电脑关机后执行任务、远程桌面操控或手机端批准的人。
- 智能家居和硬件爱好者市场：本轮不以此证明价值。

### 必须赢过的替代方式

替代品首先是“原来的 Agent 窗口、终端通知和人工记事”，不只是另一款桌宠。

如果用户只多开了一个窗口，却没有少检查终端、少漏掉等待、少翻任务结果，方案就是失败的。跨厂商接入与伙伴形象是候选差异，不是已经建立的竞争壁垒；没有完成市场调研或付费意愿验证。

## 3. 产品边界与分工

### 芯伴负责

- 显示有来源、有时间的工作状态，并指出未知和接入异常。
- 在用户选定的项目上派活；启动前按原权限规则确认。执行者由用户点名，或按「自动挑」选一个已接入的（默认）。
- 自动换的边界：只在执行者**开工前就用不了**时换下一个——没装、缺 node、起不来、没登录、启动不到 1 分钟且没有任何产出就被限流。干到一半的失败、超时、取消、自定义命令配错一律不换，结果里写明换过谁、为什么。
- 把有效、受支持的权限请求交给用户决定；不支持的明确交回原工具。
- 汇总结果、展示可检查的证据、提供打开项目和再次交代任务的入口。
- 保留可关闭的个性、记忆、文字对话与语音能力。

### 原工具继续负责

- 实际编程、安装依赖、构建、测试和执行环境。
- 芯伴无法安全承接的授权、追问与交互式流程。
- 未经正式适配的会话恢复、任务取消和终端定位。

### 本轮不做

- 另造编辑器、代码补全、通用代码 Agent 或多 Agent 自动编排引擎。
- 自动重试付费任务、自动拆单派给多个 Agent、自动提交或推送。（上面「开工前就用不了时换执行者」不属于重试：那时还没花钱、没改文件。）
- 用摄像头拍显示器代替文件、日志或用户主动提供的截图。
- 后台常开麦克风、持续截屏、猜测用户情绪或增加前台应用监控。
- 手机批准、远程执行服务器、新推送渠道、皮肤市场、更多小游戏。
- 为提高“批准率”放宽安全规则。

同时观察多个会话，不等于支持同时派发多个任务；保留当前执行并发限制，另行验证后再讨论扩展。

## 4. 三条必须做顺的使用流程

### A. 交代一件事

1. 用户选项目、输入任务；执行者默认「自动挑」，想点名就改。自然语言是可选快捷方式，不是唯一入口。
2. 展示任务原文、目标项目、执行者和执行范围；信息不明先澄清。
3. 用户确认后启动，立即回到可继续工作的界面。
4. 显示真实阶段、最近事件和取消能力，不编造进度百分比。

目标体验：知道交给了谁、在哪里干、如何停止。不得把重复点击变成两次执行。

### B. 只在需要我时找我

1. 收到可靠事件后更新任务；只是状态变化时安静更新。
2. 需要处理时，小机器人显示一条摘要；用户点击后打开对应任务或完整确认卡。
3. 支持批准回传时，展示项目、来源、完整原文、剩余时间及允许/拒绝/交回终端。
4. 不支持回传、请求过期、应用关闭或异常时，明确退回原工具，不替用户决定。

“等待授权”和“需要用户补充信息”必须区分；不能把普通追问都做成允许/拒绝。没有安全定位原终端的能力时，显示项目和会话信息让用户手动返回，不承诺一键跳回。

### C. 结束后接住结果

1. 标记“本轮执行已结束”，而不是直接宣称“需求已完成”。
2. 展示 Agent 的结论、执行结果、可见的工作区变化和测试报告来源。
3. 用户查看详情、打开编辑器、标记已看，或明确发起下一项任务。
4. 用户自行判断验收通过；“已看”不能等于“代码正确”。

真正的原会话续接需要适配器证明支持。否则入口应叫“再派一项”，并说明新任务不保证继承旧会话上下文。

## 5. 桌面交互：小机器人做入口，工作台做正事

### 5.1 小机器人

保留现有短回复、人设和表情，但将工作信息放在互动装饰之前。

- 安静时：显示必要状态，不为了刷存在感主动说话。
- 有事时：例如“有一个任务等你处理”“一项结束了，结果待看”。这些是文案示例，不是实时数据。
- 点击状态：进入对应详情；只有一项时直接定位，多项时打开按优先级排列的列表。
- 文字输入保留；语音是可选输入，识别后的任务应能检查、修改，再确认执行。
- 隐藏机器人后，托盘和工作台仍可承接核心流程；隐藏不是退出，也不是关闭权限回传，界面必须说明。
- 隐藏且没有可见提醒入口、或处于勿扰时，应明确告知权限等待仍可能占用终端时间；提供关闭回传或立即交回入口，不暗改等待时长。
- 不要求在 216×216 中阅读长命令、diff 或管理多个任务。不新增“编程搭档模式”总开关。

本轮不直接改 A/B 语义；将来确有交互变化，仍只改共享手势入口并补回归。

### 5.2 工作台作为面板主入口

建议的信息顺序：

1. **需要你处理**：有效权限、需要补充的信息、需要用户决策的失败。
2. **结果待看**：已经结束但尚未检查的任务。
3. **正在执行**：项目、执行者、阶段、最近更新时间。
4. **历史与已看**：按需展开。
5. **接入健康**：未接入、权限不足、钩子丢失、来源不支持，不能伪装成“没人等你”。

已知结果之后还有“状态不确定”的分支；过期事件不能被归成成功、失败或空闲来制造确定感。

设置按任务分组，而不是把所有技术服务堆成首页卡片：

- 项目与 Agent 接入；
- 权限与隐私；
- 外观、提醒与声音；
- 模型、记忆及可选工具；
- 高级与实验功能：硬件、模拟实验室、IoT 等保留入口但不占主流程。

这只是后续界面优化建议，本次不迁移设置、不关闭用户现有功能。

### 5.3 提醒与陪伴

- 任务变化是事实，表情是表达；表情不能决定任务状态。
- 延续本地事件、本地模板、现有打扰预算与冷却；不引入后台问模型。
- 主动提醒与持续可见的权限卡分开：提醒预算耗尽不能让权限请求或结果从工作台消失。
- 完成消息合并、重复事件去重、勿扰结束后不补播一串声音。
- 日常聊天、记忆、计时、待办、音乐和现有小游戏保留，但本轮不扩玩法。
- 语音与视觉先保证现有链路可取消、失败说清楚；不作为核心流程的使用前提。

## 6. 优先修正的四个可信度问题

以下是从代码组织得出的实施关注点，不是新的“已实测缺陷”清单。

### 6.1 会话、任务与权限必须能对上

`src/core/workbench.ts` 分别聚合外部会话和派活记录。后续应建立稳定任务 ID、来源/会话 ID 及可验证的关联；不能仅凭同一个项目名或时间相近就合并。

- 多来源证据能够关联时，呈现一项任务，不重复提醒或计数。
- 无法关联时保留“外部会话／芯伴派活”标识，说明可能相关，不强行合并。
- 权限卡绑定具体请求 ID 与参数指纹，不因切换任务而批准另一项。
- 取消、过期、重启后来源不明应有明确状态；没有运行证据不能继续显示“正在干”。

> 2026-11-12 已实现第一步（🧪）：派活时把派活 ID（开工时刻）放进子进程环境 `XINBAN_DELEGATE_ID`，钩子脚本把它写进事件，工作台把带同一 ID 的会话并进派活那条；派出去的活卡在权限请求上时，派活那条显示「等你」。对不上记录的照常当会话显示。用户自己开的会话仍不合并。待验：真实 `claude -p` / Codex / CodeBuddy 子进程是否触发钩子并继承环境。

### 6.2 工作区改动不是单项任务的成果

`src/desktop/workbench.ts` 的审阅入口读取当前工作区相对 HEAD 的变化，没有把每次派活隔离成专属 diff。

近期先如实标为“当前工作区改动，可能包含你或其他任务的修改”；未跟踪文件内容、空仓库、截断、无法读取要分别说明。已有脏工作区和并行外部编辑必须成为验收场景。

任务前基线只能辅助比较，也不能证明作者归属。本轮不为此引入自动 stash、回滚、建分支或 worktree 调度。

> 2026-11-12 已实现（🧪）：派活开工前只读记下 HEAD 和已有未提交文件数；结果卡按此说明「开工时已有 N 个文件未提交」「开工后有新提交，提交进去的不在下面」；没有基线时明确写「可能包含你或其他任务的修改」。

### 6.3 Agent 报告不等于独立验证

`WorkbenchItem.tests` 承载从派活输出识别的摘要。结果卡需分开表达：

- 进程退出结果；
- “Agent 报告的测试结果”；
- 有可信执行记录时的验证范围与时间；
- 用户验收结论。

找不到证据写“未取得测试证据”，不写“全部通过”。不在完成事件后自动运行测试；需要复验时由用户明确发起，并走原确认与执行边界。

> 2026-11-12 已改（🧪）：结果卡写「Agent 报告的测试结果（芯伴没有自己跑、也没有核实）」，认不出就写「未取得测试证据」；「干完没看」改称「结果待看」，「标记已看」注明不等于验收。

### 6.4 再派活不等于恢复原会话

`src/renderer/WorkbenchCard.tsx` 的 `followUpRequest` 通过 `aiSend` 重新交代项目与 Agent，没有构成原会话恢复契约。

近期先把入口与说明做准确；原生续接以后按工具逐项适配，不靠模型口头承诺，不把其他会话的内容自动拼过去。

> 2026-11-12 已改（🧪）：入口改名「再派一项」，输入框与发给伙伴的话都写明「新任务，不接原会话」。

### V5-01：可靠性验收清单

- [ ] 真实派一件任务：目标、目录、原文正确，启动前取消不创建进程。
- [ ] 后台执行期间对话不被占住；受支持的取消结束实际执行链路，退出状态说清楚。
- [ ] 两个同项目会话、一个不同项目会话并存，状态和权限不串线。
- [ ] 允许、拒绝、主动交回、超时、芯伴退出、钩子退出、开关关闭均有正确退路。
- [ ] 超长详情、队列满、无同步钩子的来源不假装可批准；过期按钮不再生效。
- [ ] 重复/乱序事件、休眠恢复、重启、接入失联不会误报成功或重复执行。
- [ ] 用户手动启动的外部会话和芯伴派活不会不加说明地双计；不支持的控制明确只读。
- [ ] 钩子自检在真实配置切换场景中符合“先问、已同意才自动修复”的既有规则。

没有真实验收条件就停留在对应证据等级，不为进度把未验项改成已通过。

### V5-02：少操作、少打扰

- 工作台调整为任务主入口；权限、结果和健康状态有直接入口，不埋在设置中。
- 增加或补齐结构化派活：选项目/执行者、填写任务、检查、确认、执行；不强制模型猜已选信息。
- 结构化入口必须复用主进程项目校验和 ConfirmService；不能让 renderer 直接起进程或绕过确认。
- 验收目标：从可见提醒到对应完整详情最多两次点击，不计用户阅读时间；不自动抢焦点。
- 隐藏、托盘恢复、勿扰、多个事件合并与键鼠使用均验收；必要入口要有文字，不依赖猜 A/B 或颜色。
- 不重写人格模块。确需调整提示词、人设或工具声明时，再修改统一入口并运行项目评测。

### V5-03：结果可信

- 将“进程结束”“测试报告”“用户已看/验收”分开显示。
- 检查普通 git 仓库、预先有改动、其他 Agent 同时改动、空仓库、非 git 目录、未跟踪文件和输出截断。
- diff 默认本地只读展示，点击模型总结前说明实际分享范围；不得自动上传完整代码。
- “在编辑器打开”失败给出下一步；“再派一项”明确新任务，不自动重试旧任务。
- 验收目标：任意一次成功退出但未测试的任务，不得显示成“已验证完成”。

### V5-04：接入与常驻

- 将现有首启检查按用途拆开：先接入一个 Agent 查看事件，再按需配置派活、模型和语音；不是再做一个配置系统。
- 未填芯伴模型 Key 时，目标是仍可使用已授权的本地状态观察、工作台与受支持的权限回传；原 Agent 自己的账号/运行依赖仍需满足。自然语言派活仍需模型；结构化派活由 V5-02 单独验收。
- 未接入时显示“尚未接入”，不是“没人等你”；演示数据与真实数据、统计严格分离。
- 用现有安装构建链路验收安装、启动、退出、数据保留与卸载说明；不能把解包启动当作完整安装验收。
- 在同一台 Windows 机器上记录启动耗时、15 分钟空闲 CPU/内存、隐藏动画开关差异、连续半天运行与休眠恢复。先记录基线、定位增长，再设性能预算，不引用虚构的当前性能数字。
- 现有飞书标题推送是可选增强：用户配置后再验收，不作为首次使用前置条件，不增加渠道或手机批准。

### V5-05：验证价值，而不是增加指标装饰

先确保前面几项能可靠使用，再进行 7–14 天真实工作观察。前两天保留手工基线，其余天使用芯伴处理相近任务；这只用于个人决策，不宣称因果实验或市场验证。

建议至少观察 10 件真实任务；样本不足就延长观察，不能为了凑数制造任务或权限请求。

## 8. 价值指标与停止条件

### 指标口径先校准

`src/core/usage-stats.ts` 已有本地次数与时间统计。优先复用，不再造埋点平台。

- “接住率”只对芯伴实际观察到、具备回传条件的请求计算；不是电脑上所有权限请求的覆盖率。未观察到的请求无法自动得出分母。
- 不支持来源、超长详情、关闭回传和异常交回需分开说明；看不到的部分用人工抽样对照，不把缺失数据记成零。
- “批准/拒绝”的选择都可以是有效处理；不以批准率、自动批准数作为增长目标。
- 等待时长是多会话等待时间之和，不是用户损失时间，也不能直接当成“节省了多少小时”。
- 成功退出率不等于任务验收成功率；取消和失败另外记录，不靠剔除失败美化结果。
- 模拟、测试和重复事件不计真实使用；离线、休眠和长观察间隔不填造数据。

### 建议观察的结果

| 问题                 | 记录方式                                                | 怎么判断                                                        |
| -------------------- | ------------------------------------------------------- | --------------------------------------------------------------- |
| 有没有少检查终端？   | 每日手记少检查/仍需检查的次数，不采集键盘或全局窗口轨迹 | 是否持续有具体收益，而不是一次演示好看                          |
| 有没有更快处理等待？ | 相近任务的响应时间中位数；样本数与来源一起看            | 对比本人基线，不能跨工具直接混算                                |
| 结果交接是否有用？   | 用户主动记一笔“这次少翻了记录/快速找到问题”             | 建议一周至少出现 3 次明确有用的交接；这是试用门槛，不是现有成绩 |
| 是否造成负担？       | 手记误报、重复提醒、误关联和被迫回终端的原因            | 先修影响信任的问题，不拿更多功能补偿                            |
| 还想不想用？         | 观察自然工作时是否主动保留，不要求签到                  | 关掉之后是否会想开回来                                          |

统计仅本地保存，维持现有保留上限；需要新增口径时先明确内容与清除方式。没有自动上传、项目名/命令原文/对话埋点、后台模型总结或付费的指标分析。人工笔记也尽量只记次数和问题类型。

### 决策门

- **继续**：真实流程可靠，用户持续主动使用，能举出反复发生的省心场景；再邀请少量同类开发者验证，不能把自用推成市场需求。
- **收缩**：只有状态和提醒有用，就优先做轻量观察入口，暂缓对话派活和复杂工作台扩张。
- **暂停**：仍主要依赖原窗口，新增配置、误报和打扰超过收益；不要用语音、摄像头、皮肤或硬件掩盖问题。
- **安全停止条件**：错配批准、未经确认的执行、应交回却卡住终端、敏感信息外泄，任一出现都先停相关路径并修复。

## 9. 工程与隐私约束不因定位调整而放松

- 主进程是共享状态唯一写入者；跨进程输入校验、持久化成功后发布、Electron 隔离设置保持不变。
- 权限由代码执行，不靠模型推断。现有自动批准规则、默认开关、确认超时与队列上限不在本次方案中暗改。
- 当前外部权限等待默认 45 秒、钩子 timeout 95 秒；超时交回原工具。芯伴自身工具的超时拒绝语义不变。
- 文件范围、敏感文件拦截、备份与撤销、MCP 凭据加密及默认确认保持不变。
- 会话读取开关与音视频默认关闭保持不变；模型不可用不妨碍本地事实展示和安全回退。
- 实时任务状态放在工作状态服务，不塞进长期记忆。记忆可见、可删、可关，附件仍不进入记忆抽取。
- 业务与展示解耦，复用现有 core/desktop/renderer 分层。硬件协议不参与新桌面主流程决策，也不在本轮破坏现有兼容性。
- 实施业务变更时补回归，跑 check、build、桌面 E2E；真实 Agent 验收单列。提示词、人设、工具声明或记忆注入变化再跑付费 eval，保留证据。

## 11. 下一步建议

**先做 V5-00 与 V5-01：补齐真实验收、准确状态、权限回退。** 这两步决定产品是否值得常驻；不是先重画皮肤，也不是先加语音、摄像头或更多 Agent。

只在真实流程可用之后，才进入工作台主路径和结果交接优化。最后用真实工作决定产品去留：用户留下它是因为省心，而不是因为开发了很多功能。
