# ADR-002：本轮转为桌面优先，暂停硬件主线

- 日期：2026-11-12。
- 决策状态：用户已明确要求“先不考虑硬件”，重新梳理桌面产品定位与优化方案。
- 实施状态：本次只调整定位与计划文档；功能、权限、配置、固件和默认行为未变。v5 中新增优化项仍是实施建议。
- 关联：[产品定位与优化方案 v5](optimization-plan-v5.md)、[原始 PRD](PRD-v1.0.md)、[ADR-001](ADR-001-desktop-prototype.md)。

## 背景

此前按 ESP32 实体桌面机器人规划，桌面小屏被定义为硬件到手前的模拟与调试入口。用户在选板后明确指出：不使用智能家居；没有独立音视频和编程执行能力的板卡，目前缺少实际价值。

因此，本轮不能继续以采购硬件、增加外设或完成实体装配作为产品成立的前提。需要先证明纯桌面软件能减少真实工作中的 Agent 管理负担。

## 决策

1. 本轮将芯伴定位为“有伙伴感的桌面编程助手”：交代任务、盯进度、承接用户决策、交接结果。
2. 桌面小机器人是正式使用入口，不再仅作为硬件模拟器评估。工作台承载完整任务、权限与结果；机器人保留个性和低打扰表达。
3. 硬件、IoT、外设与实体外观退出本轮主线；保留固件、协议、测试和历史文档，不删除实现，不永久取消硬件方向。
4. 复用 v4 工作，不另建一套编程 Agent、编辑器或自动调度平台；优先真实流程可靠性，其次界面、交付证据和自用验证。
5. 不增加“编程搭档模式”总开关，不以定位变化为理由删除现有陪伴能力或更改用户偏好。
6. 不改变已有授权、安全、出站和隐私规则；结构化派活等新入口也必须经过相同主进程校验与确认。

## 原始基线与历史决策的处理

- 原始 PRD 不改写为“已经完成的新需求”；需求映射与偏差写在 v5，后续证据继续写入能力清单与实施日志。
- ADR-001 的 Electron、共享主进程、受控 IPC、模拟/真实数据隔离等架构继续沿用；其 2026-11-07 的功能快照只作历史记录。
- README 的当前定位更新为本轮桌面优先；旧硬件终目标作为历史背景保留。
- v4 保留已有批准记录与工程过程；v5 是当前建议优先级，不把 v4 的代码里程碑等同于真实验收或自用验证结束。
- 功能状态仍只有 `docs/capabilities.md` 一份；本次不因文案变化提升状态等级。

## 结果与代价

- 可以在没有硬件的情况下验证核心价值，也避免因采购和固件联调分散注意力。
- 不能再把“实体按钮”作为当期差异；需要证明统一工作视图、可靠决策入口和结果交接优于原工具组合。
- 引入桌面专用详情和交互不意味着必须同步重做硬件布局；仍保留已有协议兼容，不以此绕开安全校验。
- 本次没有市场调研或付费需求证据。个人自用有效不等于商业产品已经成立。

## 复议条件

先完成 v5 的真实流程验收与 7–14 天使用观察。只有出现明确、软件入口难以满足的实体需求，并经用户重新确认后，才讨论重启硬件。不得因为代码已经写了，就把硬件重新变成默认方向。
